# Cloudflare Pages Functions

Run the site locally from `gallery/` with `npx wrangler pages dev .`. Set the Firebase project ID and admin email list in local Wrangler configuration or with environment variables. Bind KV or R2 as `PHOTOS`; for the private Google Cloud Storage route set `PHOTOS_BACKEND=firebase`, `FIREBASE_STORAGE_BUCKET`, and the `GOOGLE_SERVICE_ACCOUNT_JSON` secret. Never put credentials in `wrangler.toml`.

Before deployment, check the KV namespace id and Firebase project id in `wrangler.toml`, set `ADMIN_EMAILS` as a Pages secret (`npx wrangler pages secret put ADMIN_EMAILS`), and make sure the Pages project has the intended `PHOTOS` KV/R2 binding. For Firebase Storage, configure a private bucket and a service account with object access scoped to that bucket; set `GOOGLE_SERVICE_ACCOUNT_JSON` as a Pages secret and `FIREBASE_STORAGE_BUCKET` as a nonsecret Pages variable. Keep the bucket's direct-client Storage Rules denied; all browser requests pass through authenticated Pages Functions. Deploy with `pipeline/deploy_cloudflare.ps1 -Deploy` (it uploads only the built `dist/` folder and puts the data JSON in the active store). Never run `wrangler pages deploy .`: that publishes every file in `gallery/` including `data/`. Firebase users must have access to their own Firestore `users/{uid}` document for status checks.

Run the function unit tests with `node --test functions/tests/*.test.mjs` from `gallery/`.

## Ingest, upload status, and storage endpoints
- `POST/GET/DELETE /api/admin/fb-cookies`: Facebook session cookies for the `scan` workflow. Write-only: `GET` returns presence, size and date, never the cookies. Stored under `secrets/fb-cookies.txt` (and the optional page URL under `secrets/fb-url.txt`) in the `PHOTOS` store.
- `POST/GET /api/admin/scan`: dispatches to / reads the latest run of `.github/workflows/scan.yml`. Dispatches target `automation/scan`; the POST accepts `fetchFacebook`, `recluster`, `reembed`, and `migrateFrom` (`kv`, `r2`, or `firebase`).
- `POST/GET /api/admin/uploads`: lists processed review items and raw pending count; POST `{photo, action}` writes an approval/rejection marker for the pipeline.
- `POST /api/uploads/check`: checks up to 30 exact SHA-256 values against the private catalog and the signed-in user's queued files before the browser sends image bytes. `/api/upload` repeats the catalog and queued-file checks and refuses an exact duplicate before writing it.
- The admin Uploads tab groups processed review items by uploader, expands thumbnails to the full web image and can approve that user's current review snapshot in one click. Batch approval writes one marker; later uploads are not included in an earlier click.
- `GET /api/uploads/mine`: approved users see their processed upload states and raw uploads still queued.
- `GET/POST /api/admin/storage`: reports the scanner target (`STORAGE_BACKEND`) separately from the live API route (`PHOTOS_BACKEND`/`PHOTOS`), and can set `STORAGE_BACKEND` to `kv`, `r2`, or `firebase`. Firebase selection requires a stable, hash-verified `migration/kv-to-firebase/manifest.json` in the private bucket and an active `SCAN_HOLD`; selecting it does not itself switch live upload routing.
- `SCAN_HOLD=true` pauses automated and admin scans while uploads continue to be accepted and queued. Keep the hold through the final delta sync and live route cutover. The Actions workflow also checks the repository variable so new scans are skipped immediately during deployment.
- `UPLOAD_HOLD=true` is a short final-cutover gate. Pages returns a clear retry response before touching storage; release it after the Firebase API deployment is active. Keep `SCAN_HOLD=true` until end-to-end upload and scan checks pass.
- GitHub calls need `GITHUB_DISPATCH_TOKEN` and `GITHUB_REPO`. The fine-grained GitHub token needs Actions: read/write and Variables: read/write on this repository only.
- Storage object keys are shared between KV, R2, and Firebase Storage: `pending/<uid>/<sha256>/<ms>-<uuid>.<jpg|png|webp>` raw uploads until processed; `state/catalog.json` exact-hash index (`sha` for normalized pixels and `upload_sha` for original upload bytes); `status/scan.json` scan state; `status/uploads/<uid>.json` per-user states; `status/storage.json` backend usage; `migration/kv-to-firebase/manifest.json` migration inventory and verification; `data/pending.json` admin review queue; and `review/<photo>.json` or `review/batches/<id>.json` approval markers consumed and deleted by the pipeline. Photo IDs match `p` plus eight lowercase hexadecimal digits.
- Workflow credentials: `GOOGLE_SERVICE_ACCOUNT_JSON` is the same private service-account JSON secret in Pages and GitHub Actions; `FIREBASE_STORAGE_BUCKET` is the bucket name. Keep the bucket private and limit the service account to object access on that bucket.
- Workflow secrets: `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` and optionally `IMG_KEY` (obfuscates image names). R2 objects the job expects: `people/identities.json` + `people/reference_faces/`.
